# Git Standard

本文件规定本项目的 Git 使用标准。目标是让提交历史清晰、分支职责明确，并减少协作时的冲突成本。

## 基本原则

- 每次提交只表达一个清晰目的，避免把无关改动放进同一个 commit。
- 提交前先检查变更内容，确认没有误提交临时文件、密钥、构建产物或无关修改。
- 修改已有文件时优先遵循当前代码和文档风格，不做无关重构。
- 文档统一放在根目录 `docs/` 文件夹中；新增项目文档不要放到 `doc/`。

## 分支规范

分支名使用小写英文、数字和连字符，建议格式如下：

```text
<type>/<short-description>
```

常用类型：

- `feature/`：新功能。
- `fix/`：问题修复。
- `docs/`：文档变更。
- `refactor/`：不改变行为的代码整理。
- `chore/`：工具、配置、依赖等维护性变更。

示例：

```text
feature/user-login
fix/post-pagination
docs/git-standard
chore/update-dependencies
```

## 提交信息规范

提交信息使用简洁中文，建议采用以下格式：

```text
<类型>：<摘要>
```

常用类型：

- `功能`：新增功能。
- `修复`：修复问题。
- `文档`：文档变更。
- `重构`：不改变行为的代码整理。
- `测试`：测试相关。
- `维护`：工具、配置、依赖等维护性变更。

示例：

```text
文档：新增 Git 使用标准
修复：处理空帖子列表
功能：新增话题创建表单
```

提交说明要求：

- `<summary>` 控制在一行内，说明本次提交做了什么。
- 不使用含糊描述，例如 `更新`、`修改`、`杂项`。
- 如果一次改动包含多个互不相关的目的，拆成多个 commit。

## 日常工作流程

开始工作前：

```bash
git status
git pull --rebase
```

开发过程中：

```bash
git status
git diff
```

提交前：

```bash
git status
git diff --check
```

提交：

```bash
git add <files>
git commit -m "<类型>：<摘要>"
```

## 合并与同步

- 合并前先确保本地工作区干净。
- 拉取远端更新时优先使用 `git pull --rebase`，减少无意义的 merge commit。
- 处理冲突后必须重新检查相关文件，确认冲突标记已清理。
- 合并或发起 PR 前，根据改动类型运行必要验证，例如测试、构建或格式检查。

## 文档位置规范

- 新增项目文档统一放在根目录 `docs/`。
- 文档文件名使用小写英文和连字符，例如 `git-standard.md`。
- 每个文档应有明确标题，并在开头说明用途。
- 如果需要新增文档分类，可在 `docs/` 下建立子目录，例如 `docs/design/`、`docs/process/`。

## 禁止事项

- 不提交密钥、令牌、私有证书或个人环境配置。
- 不在未确认影响范围的情况下执行破坏性 Git 命令，例如 `git reset --hard`。
- 不把无关变更混入同一个提交。
- 不把临时调试输出、缓存文件或构建产物作为项目源码提交。
